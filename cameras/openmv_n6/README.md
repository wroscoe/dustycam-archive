# openmv_n6 — `n6cam`

An **OpenMV N6** (STM32N657) camera on the shared MicroPython runtime of
[`docs/camera_standard.md`](../../docs/camera_standard.md) and
[`docs/camera_operation.md`](../../docs/camera_operation.md). Board serial
`31001c00025043364d343000`, firmware 5.0.0 / MicroPython 1.28 (v1.28.0-49).
Second N6 (`004C347E3643`) not yet migrated.

**Status: designed.** The `game_lowpower` off-grid profile (PLAN.md,
written and host-tested 2026-09-13) is **unflashed**. The board's flash
currently runs the older **monitor** profile firmware, **live** at app
2.0.10-n6 (power = `always_on`, proven 2026-09-03), reporting as `n6cam`:
http://192.168.86.26:8088/d/n6cam — that stays live until this bundle is
staged (`tools/dustygen cameras/openmv_n6 --stage`) and pulled, or copied
over USB. See [`PLAN.md`](PLAN.md) for the full design this README
summarizes.

Both profiles run from the same bundle (`app.py`'s dispatch: `game_run` if
`TUNING['profile'] == 'game_lowpower'`, else the always-on loop) — see
"Profiles" below.

## Board facts

(Firmware 5.0.0 / MicroPython 1.28.) Legacy `sensor` API works; `machine.LED`,
`ssl.SSLContext`, `json` present; pins `SW` (user button, active-low), `CHG`
(active-low charging), `BAT_ADC`, `LED_RED/GREEN/BLUE` (`LED_BLUE` = B1,
`LED_GREEN` = A7, `LED_RED` = G10), `ONOFF` (PA2, WKUP2). Sensor: CSI camera,
native HD 1280x800 (VGA 640x400, QVGA 320x200 — 16:10, not 4:3); the CSI
**rejects JPEG and YUV422 pixformats**, so captures are RGB565 at HD +
software JPEG. Framebuffer pool 32 MB (20 MiB usable), fb cost = w×h×2 for
every format. `BATT_DIVIDER` 1.5 is inferred, not measured.

**`game_lowpower` bench facts (PLAN.md §0, proven 2026-09-13):**

| fact | proven |
|---|---|
| `machine.deepsleep()` is STM32 standby; `machine.RTC().wakeup(ms)` wakes it | yes: 10 s and 5 s sleeps, `reset_cause() == DEEPSLEEP_RESET (4)` |
| RTC survives standby | yes: a deliberately set 2031 date came back advanced by the sleep |
| TAMP backup registers survive standby | yes: `stm.mem32[stm.TAMP_NS + 0x100 + 4*i]`, two words written before, read back after |
| `RTC.wakeup(43200000)` (12 h) accepted | yes (cancelled with `wakeup(None)`) |
| USB drops ~1.1 s after `deepsleep()`, re-enumerates ~2 s after the wake; `ticks_ms()` ≈ 1.07 s when main.py starts | yes |
| `ml.Model()` loads a ROM model, exposes `input_shape/scale/zero_point`, `predict` | yes (`/rom/person_detect.tflite`) |
| `sensor.shutdown()`/`sensor.sleep()`; `network.WLAN.deinit()` exist | present, effect on sleep current unmeasured |
| user button `SW` = PF4 (pull-up), LEDs B1/G10/A7, `ONOFF` = PA2 | neither USER nor PWR wakes standby; `machine.lightsleep()` never returns (see bench gates) |
| SD card (30 GB, FAT) | fitted 2026-09-13 with the chain loader; 1 MB write 83 ms, read 52 ms; standby wake through the chain loader works |
| Wake cycle on the device | 2.1.x: ~2.6 s awake per wake, boot/motion frames on the card, wake log written |

Open, needs a meter: standby current. RTC drift needs contacts over weeks.

Firmware quirks found on the device (all handled in the code):

- **Tuple attributes, not methods (fw 5.x):** `get_histogram().l_bins`,
  `blob.rect` and the `get_statistics()` fields are values; `board.py`
  checks `callable()` before calling. `draw_rectangle` wants the tuple
  form like `draw_string`.
- **The first `ml.Model()` of a boot fails** (`RuntimeError: Failed to load
  network`), the second succeeds; `judge.gate_init()` retries once and only
  blacklists a model when both attempts fail.
- **Every `sensor.reset()` re-converges AWB/AGC** to slightly different
  values: a static scene diffs 10–16 % of thumbnail pixels at `|dL| >= 8`,
  ~0 at `>= 24`. Hence `diff_l_thresh = 24` for this profile (the monitor
  profile's 8 is only valid within one sensor session). sarg:
  `sargbench2/openmv-n6-fw-5-0-0-the-first`.
- **USB-copying a build over a pending OTA install** makes the next boot's
  `fw_boot_check` blacklist the pending version as "crashed" (harmless when
  it is superseded; delete `fw_bad.txt` if it matters).
- The console loses the wake line more often than not (USB re-enumerates
  every wake); `/sdcard/wakelog.txt` is the record.

Deny list (hard-hangs the MCU, bypasses rollback): `pyb.ADCAll` /
`read_core_temp` while streaming; `sensor.set_frame_callback()`; `cpufreq`
unproven — none of these are called.

## Profiles

`profile` is a tuning key (`camera.toml [tuning]`), pulled at every config
refresh — switching it is a config change, not a reflash:

- **`monitor`** — the board as it ran through 2026-09-03: always on,
  `wifi_linger_s` optionally cycles the radio, motion/heartbeat trigger,
  live upload with spool as a fallback (inactive here: no SD card).
- **`game_lowpower`** — this pass: wake cycle, deep sleep between wakes,
  night sleep, spool to SD, drain at contact
  ([`docs/camera_operation.md`](../../docs/camera_operation.md) §4.1). This
  is now `camera.toml`'s default (`power = "wake_cycle"`).

`app.py`'s `run()` dispatches to `game_run(poll)` (from `wakecycle.py`)
when `TUNING['profile'] == 'game_lowpower'` and falls through to the
always-on loop otherwise, so one bundle serves both.

## The wake

One wake (`wakecycle.py`, PLAN.md §3): `wake_cause()` (`deep` / `cold` /
`soft`), load the backup-register state, then:

1. **Contact first** when the button is held, on **any cold boot**
   (power-on, PWR button off/on, watchdog — not a `'soft'` reset), on the
   first non-cold boot after provisioning, or while a firmware install is
   still proving itself (`fw_pending`), card or no card.
2. No card → LED fail pattern, one wake-log line, sleep `period_s`.
2b. **`bench_contact_n`** (dev/bench only, `0` disables it): every Nth wake,
    scan for the home LAN before anything else; if it's visible, run a
    contact (bench OTA/config without the button).
3. **Sense**: `preview_init(preview_settle_ms)`, one VGA RGB565 snapshot,
   `lum` = `board_lum()` (LAB L 0–100 scaled to 0–255).
4. **Night**: `night_step()`; entering or probing night records nothing and
   sleeps `sleep_s`; leaving night marks the morning frame with `night_s`.
5. **Watch**: 80×50 grayscale thumbnail diffed against the last *recorded*
   thumbnail from the card (`board_thumb_diff` → fraction + largest blob).
6. **Trigger**: `boot` (no reference) → `motion` (`diff ≥ diff_min_frac`) →
   `interval` (`wake_n % interval_n == 0`) → `heartbeat` (`awake_ms ≥
   heartbeat_s·1000`, awake time only, like the XIAO) → `none`.
7. **Judge** only for `motion`, on the preview before the capture (the
   preview aliases the frame buffer): `gate_init()` with the hard-fault
   guard, `crop_box()` around the diff blob in preview coordinates,
   `gate_score()`, `judge_decide()` (pass / keep_all / 1-in-`audit_n` audit /
   reject). Any failure keeps the frame with an empty `det`. A rejected
   motion frame still moves the reference thumbnail on so the same change
   does not re-trigger every wake.
8. **Debug frame** (`debug_frames`): the preview as JPEG q60 with
   `why: watch` under `/sdcard/debug/<boot>/<wake_n>`.
9. **Capture + Record**: HD RGB565 → JPEG q85, sidecar with the standard
   keys plus `score`, `clock`, `lum`, `det` (and `night_s`), written under
   `/sdcard/spool/<boot>/<seq:06d>`; reference thumbnail saved; 50 ms LED
   blink if `led_capture`.
10. Button poll → contact. Save state (`awake_ms += ticks_ms()`,
    `crash_n = 0`), append the wake-log line, `board_rest(period_s)`.

Any exception in a wake is logged, counted in `crash_n` and still ends in
`board_rest()`; three in a row and the board rests ten periods instead.
`board_rest()`: `sensor.shutdown()`, WLAN deinit, `machine.RTC().wakeup(ms)`,
`machine.deepsleep()` — never returns; `main.py` reruns on the next wake
with `reset_cause() == DEEPSLEEP_RESET`. With `SLEEP_MODE = 'light'`
(`machine.lightsleep`, the fallback if the button cannot wake standby)
`board_rest()` returns and `game_run()` loops.

**Loader contract (`/flash/wake_cycle`):** `ota_main.py` skips WiFi, NTP
and the OTA listener whenever `reset_cause() == DEEPSLEEP_RESET` or the
flag file `/flash/wake_cycle` exists. `wakecycle.py` writes the flag once
on a cold boot (never per wake) and the monitor profile's loop removes it,
so a profile switch back takes effect at the next reboot. The flag covers
the first cold boot after flashing and any non-deep-sleep reboot mid-cycle
(crash, watchdog). Recovery mode always brings WiFi up itself, so a broken
`app.py` is still reachable over the hotspot.

## Contact

Exactly [`docs/camera_operation.md`](../../docs/camera_operation.md) §5,
implemented in `contact.py`. A contact starts on: a button press (any
stage), **any cold boot** (power-on, **PWR button off/on** — the field
gesture for a contact in the field — or a watchdog reset; a battery swap
costs one search), the first non-cold boot after provisioning, or a
firmware install still proving itself (`fw_pending`). A `'soft'` reset
(mpremote, an OTA install's own reboot) is not a deliberate field gesture
and keeps the old first/pending-only rules.

**Two networks, chosen by a scan before joining:** `contact_scan()` scans
first and, if the home LAN's `LAN_SSID` (from `~/.dusty/secrets.toml
[wifi]`) shows up, joins it and points `uplink.py` at
`LAN_HOST/LAN_PORT/LAN_TLS` (`~/.dusty/config.toml [server]` host +
`gate_port`, no TLS) for the rest of the contact via `set_server()`;
otherwise it joins the phone hotspot (`secrets.WIFI_SSID/WIFI_PASS`, from
`~/.dusty/secrets.toml [hotspot]`) as before — even if the scan missed it
(scans can miss) — and `set_server(None)` keeps the public/Funnel path.
Either way: clock set from the `Date` header → announce telemetry
(`mode: 3`) → firmware check then config pull → ranked drain of the SD
spool up to `upload_cap`, then debug frames up to `debug_max` → serve the
control plane / setup page until `contact_idle_s` idle → leave (final
telemetry, radio off, `set_server(None)` restored, motion reference reset,
reclaim). LED language below.

**Bench auto-contact (`bench_contact_n`, tuning key, default `0`):** on a
bench within reach of the home LAN, set `bench_contact_n` > 0 and every Nth
wake scans for the LAN and, if seen, runs a contact — OTA/config over the
LAN without holding the button (`wakecycle.py`'s `_one_wake`, using
`contact_scan_lan()`, the same scan `contact_run` itself uses to choose LAN
vs. hotspot).

## Night

Daylight-only, radio off, no clock or location (`night.py`):
`lum < lum_night` for `night_confirm_n` consecutive wakes → night; sleep
until the predicted dawn (median of the last 3 learned night lengths) minus
`night_margin_s`, then probe every `night_probe_s`; `lum ≥ lum_day` on a
probe → day, morning frame `why: boot` carries `night_s`. `lum` comes from
`board_lum()`: OpenMV's LAB stats report L as 0–100 on the N6 (not 0–255),
scaled ×2.55 so `lum_night`/`lum_day` mean the same fraction of full
brightness as on the XIAO.

## Storage

**No SD card fitted yet** — `game_lowpower` is not applicable until one is.
**With a card in, the firmware boots from the card**, not from `/flash`:
`/sdcard` becomes the boot filesystem and cwd, `main.py` is looked up
there, and an empty card boots to a bare REPL with no error (sarg:
`sarg/openmv-n6-silently-skips-flash-main-py-autorun`). So the card carries
a two-line chain loader, `/sdcard/main.py` = `exec(open("/flash/main.py").read())`,
and everything else stays on `/flash`. `software/host/prep_sd.py` writes
that loader plus `spool/` and `debug/` over USB with the card in the board,
reports size, free space and a 1 MB write/read timing, and resets. The
board's USB mass storage shows the card instead of `PYBFLASH` while a card
is in, so copy files to `/flash` with `mpremote cp` (below), not through
the mounted drive. Once
fitted: `/sdcard/spool/<boot_count>/<seq:06d>.jpg` + `.json` (sidecar
first, image to `.tmp`, rename), `/sdcard/debug/<boot>/<wake_n>.jpg+.json`
for `debug_frames`, reclaim at `spool_max_frames`. Names never use the
clock (PLAN §9/§10). The wake log (`/sdcard/wakelog.txt`, one line per
wake, rotated at 1 MB) and the reference thumbnail live on the card too;
only `night.json` (written at night transitions) and `boot_count.txt`
(cold boots) are on `/flash`, so nothing on NOR is written per wake.

## Judge

The camlogger's `gate.tflite` (MobileNetV2-0.35, 96×96×3 int8, output
`[p_not_animal, p_animal]`; **no retraining**), converted for the N6's
Neural-ART NPU with the tools the OpenMV IDE bundles (stedgeai, its
python, arm-none-eabi-gcc — nothing installed):
`software/host/convert_gate.sh` → `software/app/gate.tflite` (522,816
bytes). The output is an `NBIN` relocatable binary, the same format as the
board's `/rom/*.tflite` models; it keeps the `.tflite` name so
`board.py`'s `GATE_MODEL = '/flash/gate.tflite'` stays generic. **USB copy
only, never OTA'd**, same rule as `secrets.py`. Bench 2026-09-13 (loaded
from a host-mounted directory, no flash touched): 54 of 55 epochs on the
NPU (Softmax in software), `ml.Model()` reports input (1,96,96,3) int8,
output (1,2); `predict()` returns dequantised floats, 3 ms at 96×96 and
5 ms with a VGA image auto-scaled. Loading through mpremote's `/remote`
mount is flaky (the first load raises, later ones sometimes reset the
board), so the real load test is on `/flash` with the guard below (sarg:
`sargbench2/convert-a-custom-tflite-for-the-openmv-n6`).

Hard-fault guard (`judge.py`): write `/flash/model_pending.txt` before
`ml.Model()`, remove it after; a leftover marker at boot becomes
`/flash/model_bad.txt` (with the file size) and the gate stays open until a
differently sized model file appears. Every other failure (no model, load
error, predict error) also fails open: keep the frame, empty `det`.
`gate_score()` takes output index 1 (`animal`, as `gate.cc` on the XIAO) or
the `animal` label when the model carries labels. Crop: the motion-diff
blob scaled from the thumbnail to the preview, square, padded 50 %,
clamped, at least 96 px; the full frame when the mask covers more than
60 % of it.

## Deploy

**Field path:** hold USER to start a contact, open the device page's setup
link, and change a value on its settings form — it is written straight to
`/hd2/sensorhub/config/n6cam.json` and the board picks it up at the next
config pull. That server file is the live source of truth once a board has
pulled it.

**Workstation path** only *seeds* that file: it fills in a tuning key
that isn't on the server yet and never overwrites one already there (a
`drift` line is printed instead) — pass `--reset-config` to force the
server back to the workstation's values. Everything starts from
`~/.dusty/config.toml [camera.openmv_n6]` and
`~/.dusty/secrets.toml` — **which now needs a `[hotspot]` section**
(`capabilities` includes `hotspot`; `dustygen` exits with a hint if it is
missing):

```toml
# ~/.dusty/secrets.toml
[hotspot]
ssid = "..."
password = "..."
```

```bash
tools/dustygen cameras/openmv_n6 --stage    # --public is now the default (hotspot); --lan forces the LAN gate
curl -X POST http://<camera ip>:8266/refresh    # or wait for the next contact
```

writes `software/app/secrets.py` (WiFi = the hotspot creds, server =
Funnel host/TLS by default, **plus `LAN_SSID/LAN_PASS` from
`~/.dusty/secrets.toml [wifi]` and `LAN_HOST/LAN_PORT/LAN_TLS` from
`~/.dusty/config.toml [server]` host + `gate_port`, so a contact can pick
the home LAN by scan** — see "Contact" above), stamps `TUNING` into
`board.py`, seeds
`/hd2/sensorhub/config/n6cam.json` (adds any tuning key missing there,
leaves a value already present alone, bumps `cfg` only if it changed —
`--reset-config` to overwrite it from the workstation values instead),
rewrites `n6cam.schema.json` (types/defaults/help for the settings form)
every run, bundles `software/build/app.py` per `camera.toml [bundle]
order`, and with `--stage` copies it to `/hd2/sensorhub/firmware/n6cam.py`
+ `.version`. **Bump `APP_VERSION`** in `board.py` for every staged build
(dustygen restamps `TUNING` only).

### First deploy / any loader change (USB)

The board enumerates as
`/dev/serial/by-id/usb-MicroPython_Pyboard_Virtual_Comm_Port_in_FS_Mode_31001c00025043364d343000-if00`.
Its USB drive is `PYBFLASH` without a card and the card itself with one, so
write `/flash` through `mpremote`, which works either way. Unmount whatever
drive the board exposes first (the host's FAT mount racing the board's own
writes is the classic way to corrupt it).

```bash
P=/dev/serial/by-id/usb-MicroPython_Pyboard*-if00; A=software/app
udisksctl unmount -b /dev/sdX                      # the board's drive, whichever it is
mpremote connect $P cp $A/secrets.py :/flash/secrets.py + cp $A/ota.py :/flash/ota.py \
    + cp $A/ota_main.py :/flash/main.py + cp $A/gate.tflite :/flash/gate.tflite \
    + cp software/build/app.py :/flash/app.py + reset
```

**The `ota_main.py` (loader) change in this pass needs a USB copy** to take
effect on the currently-live board — the loader is never OTA'd, by design
(a bad push can't brick the update loop). Unmount before any reset (OTA
install, rollback test, `bench_sleep.py`): the host's mounted FAT and the
board writing `/flash` at the same time is the classic way to corrupt it.

## Phone-side facts

([`docs/camera_operation.md`](../../docs/camera_operation.md) §5.) The
owner's Android phone hotspot must be set to **2.4 GHz** (or "extend
compatibility") — the N6's radio needs it. The phone stays on cellular
data the whole time the camera is attached; nothing is stored on the phone.
The sensorhub device page is opened over cellular, but its **setup** link
points at the hotspot's private-network IP, which the phone routes locally
to the camera — that link only works while the phone is joined to the
camera's hotspot.

## LED language

([`docs/camera_operation.md`](../../docs/camera_operation.md) §10 is the
cross-board reference; one LED, `on`/`off` only, is the lowest common
denominator — the N6 uses `LED_BLUE` (`LED_NAME` in `board.py`) as that
channel and adds no pattern the XIAO cannot show.)

| State | Pattern |
|---|---|
| unprovisioned | double blink every second |
| searching for the hotspot | one blink per second |
| contact, draining | solid |
| settings updated | three quick blinks, then solid |
| contact failed | five fast blinks, then off |
| live | off; one 50 ms blink per recorded frame if `led_capture` |
| night | off |
| recovery | one blink every two seconds |

## Serial / wake log format

Console: `software/host/monitor.py` (reconnects on every reset **and**
every deep-sleep wake — the USB port re-enumerates both times). One line
per wake, appended to `/sdcard/wakelog.txt` (rotated at 1 MB) and also
printed to the USB console:

```
wake_n cause lum diff why kept score awake_ms sleep_s
```

`cause` is `wake_cause()`'s `deep`/`cold`/`soft`; `why` is `boot` / `motion`
/ `interval` / `heartbeat` / `none`; `kept` is 1 only when a frame was
actually written to the spool this wake. During a contact, expect
`contact`/`judge`/`night`-tagged lines mirroring the XIAO's format
(`cameras/xiao_pantilt/README.md` "Serial commands / log format").

## Bench gates

(PLAN.md §8, in order; each result goes in sarg — `software/host/
bench_sleep.py` drives most of these; **not yet run**, owner-only.)

- [x] **Standby, RTC survival, backup-register survival** — proven
  2026-09-13 on the bench (see the table above): `reset_cause() ==
  DEEPSLEEP_RESET`, RTC advanced correctly through standby, TAMP registers
  read back unchanged, USB timing measured.
- [x] **SD card fitted**: answered by sarg (the card takes over the boot
  and the USB drive) — `prep_sd.py` puts the chain loader on the card;
  `bench_sleep.py sd` then confirms the loader still starts and times the card.
- [x] **Button wake from standby**: **no** (2026-09-13, two 60 s runs with
  USER pressed: the port returned at ~61 s both times; `SW` is PF4, not a
  wake-up pin). **Light sleep is unusable**: `machine.lightsleep(60000)`
  with a pin IRQ never returned, USB dropped and the board needed a power
  cycle (sarg: `sargbench2/openmv-n6-fw-5-0-0-the-user`). So the profile
  runs standby + RTC only, and the button is polled at every wake: **hold
  USER until the LED answers, up to one `period_s`**. The PWR button (`ONOFF`, PA2) did not wake standby either in one 60 s
  run. A hardware button on a real WKUP pin is the fix if holding USER is
  not acceptable.
- [ ] **Standby current** with a meter in series with the pack, with and
  without `sensor.shutdown(True)` and `wlan.deinit()`.
- [x] **Hotspot join time**: 3.0–3.5 s from `wlan.connect()` to an IP on
  the phone (RSSI −35 next to it, four contacts); two of five attempts found no hotspot
  because Android had switched it off while idle (turn that setting off).
- [x] **Upload throughput** through the phone: ~2.4 s per 150 KB frame
  (0.1 s connect, 1.0–1.5 s TLS handshake, 0.7 s body at ~200 KB/s, 0.25 s
  response), so ~60 KB/s and about 40 min for a 1000-frame drain. A first
  run at 9 s per frame was the phone's own WiFi being on: Android shares the
  hotspot through the WiFi uplink and the radio time-slices. Write size and
  WLAN power mode made no difference. `upload_cap` 1000 is fine.
- [ ] **RTC drift**: `clock_skew_s` at each contact over two weeks.
- [x] **Gate load and timing**: loads from `/flash` with the guard (after
  the retry for the first-call failure), predicts in 3 ms on the NPU.
- [ ] **Wake cost**: ms from `main.py` start to `deepsleep()` for a
  no-motion wake (target < 1.5 s; `preview_settle_ms` tuning).
  `bench_sleep.py wake_cost`.
