# xiao_pantilt — `xiaocam1`

A **Seeed Studio XIAO ESP32S3 Sense** (OV3660, 8 MB flash, 8 MB PSRAM,
microSD) run as a **static** camera in `hardware/tubecase`, on the
`game_lowpower` profile ([`docs/camera_operation.md`](../../docs/camera_operation.md)
§4.1): deep-sleep between wakes, motion/interval/heartbeat trigger, an
on-device gate, frames spooled to SD. It is **off-grid**: there is no LAN
and no internet at the site, so the camera never phones home on its own —
the owner walks up, presses the button, and the camera joins the owner's
Android phone hotspot to drain its spool, pull config/firmware, and report
telemetry (`docs/camera_operation.md` §5). Between contacts the radio is
off; at night it sleeps through the dark and probes for daylight.

This is the third id for this hardware line. The camera used to be a
pan-tilt head (`xiaopantilt`); that software and mechanism are kept for
reference under [`archive/pantilt/`](archive/pantilt/) and were never
deployed. The board is now fixed in a tube case; the device id is
**`xiaocam1`**.

**Status: designed.** Camera + microSD proven **2026-09-12** on the Arduino
bench sketch ([`software/bench/sd_camera_test/`](software/bench/sd_camera_test/)):
real OV3660 (PID `0x3660`), UXGA JPEG capture, SD write, on the assembled
head with a 64 GB SDHC card. **Firmware is unflashed** — the ESP-IDF app
(`software/app/`), the shared `cameras/common/espidf` components, and the
wake/contact/night loop described below exist as this plan and (as of this
package) `dustygen` support + manifest + skeleton files, not yet as a
running board. Everything under "Standard mapping" is intent unless marked
proven.

See [`PLAN.md`](PLAN.md) for the full design (this README summarizes it)
and [`docs/camera_operation.md`](../../docs/camera_operation.md) /
[`docs/camera_standard.md`](../../docs/camera_standard.md) for the
cross-camera contract this implements.

## Deploy

Field tuning happens on the device page's settings form during a contact
(hold BOOT); `dustygen` only *seeds* `xiaocam1.json` on the sensorhub for
keys not already set there, never overwriting one, unless `--reset-config`.

Everything starts from `~/.dusty/config.toml` `[camera.xiao_pantilt]` and
`~/.dusty/secrets.toml` (needs a `[hotspot]` section — see "Phone-side
facts" below):

```bash
tools/dustygen cameras/xiao_pantilt --stage
```

writes `software/app/sdkconfig.secrets` (identity, WiFi, server host/port/TLS,
blob token), stamps `software/app/main/tuning_defaults.h` from `camera.toml`
`[tuning]`, seeds `/hd2/sensorhub/config/xiaocam1.json` with that tuning
(missing keys only, `cfg` bumps only if it actually changed) and rewrites
`xiaocam1.schema.json` every run, and
with `--stage` copies `software/app/build/xiaocam1.bin` +
`software/app/version.txt` to `/hd2/sensorhub/firmware/` as `xiaocam1.bin`
+ `xiaocam1.version`. `--public` (the Funnel host/TLS) is the default for
this camera because `capabilities` include `hotspot`; pass `--lan` to force
the LAN gate instead. There is no bundling step (unlike the MicroPython
cameras) — the ESP-IDF build already produces one `.bin`.

Build (Docker, ESP-IDF 5.5, no host toolchain) and flash:

```bash
make -C software/app build            # espressif/idf:release-v5.5, hermetic
make -C software/app flash PORT=/dev/ttyACM1   # first flash over USB
```

Component cache (`managed_components/`, `dependencies.lock`: esp32-camera
2.1.7, esp-tflite-micro 1.3.7, esp-nn 1.2.5, esp_jpeg) is copied in ahead of
time so the Docker build needs no network. Not yet run for real — the
`Makefile` and `main/` sources land with work package A3/B.

## Phone-side facts

(`docs/camera_operation.md` §5.) The owner's Android phone hotspot must be
set to **2.4 GHz** (or "extend compatibility") for the XIAO's radio to see
it. The phone stays on cellular data the whole time the camera is
attached — nothing is stored on the phone itself. The sensorhub device page
is opened over cellular as usual, but its **setup** link points at the
camera's hotspot IP, which the phone routes locally to the camera's control
plane; that link only works while the phone is actually joined to the
camera.

## LED language

One LED, `on`/`off` only (`docs/camera_operation.md` §10 is the
cross-board reference). **XIAO deviation** (`PLAN.md` §7): GPIO21 is both
the user LED and the SD chip select. While the card is mounted the pin is
routed to the SPI peripheral, so the LED task is suspended and the card's
own chip-select activity is what the LED shows. The firmware therefore
mounts the card only when it needs it: during the wake cycle's record, the
contact's drain, and the leave-time reclaim. Every other pattern is shown
with the card unmounted.

| State | Pattern | XIAO note |
|---|---|---|
| unprovisioned | double blink every second | as specified (card unmounted) |
| searching for the hotspot | one blink per second | as specified: contact unmounts the card before the search |
| contact, draining | solid | **deviation: card-activity flicker instead of solid**, the drain owns the pin |
| settings updated | three quick blinks, then solid | as specified, shown for 0.7 s before the drain takes the pin |
| contact failed | five fast blinks, then off | as specified, shown for 0.9 s before the wake cycle takes the pin |
| serving the setup page | solid | as specified (card unmounted; `Shoot` uploads straight from the frame buffer) |
| live | off; one 50 ms blink per recorded frame if `led_capture` | the blink is queued after the card unmounts, just before sleep |
| night | off | as specified; the pin is held high (card deselected) through deep sleep |
| recovery | one blink every two seconds | as specified (no card) |

## Standard mapping

One row per stage of `docs/camera_standard.md` §2, plus the two operation
stages this camera adds (`docs/camera_operation.md` §3). All of this is
**planned**, not yet running — see the status line.

| Stage | How `xiaocam1` does it |
|---|---|
| Boot | RTC magic+crc check (`app_state.c`; cold boot: zero RTC, NVS `boot_count++`, thumbnail invalid, clock `none`); wake cause timer / ext1 GPIO0 / cold; `dusty_ota_boot_check` logs a rollback; `dusty_config_init` (tuning_defaults.h defaults + NVS override); a pending firmware verify, or the button held ≥ 3 s at cold boot, or 3 consecutive `ESP_RST_PANIC` boots (NVS `crash_n`, cleared on a clean wake) enter **Recovery** or **Contact** before any sleep |
| Connect | Folded into **Contact** below, not run every wake: `esp_wifi` STA join to the phone hotspot, up to `hotspot_join_s`, retried up to 3 times when a pending-verify image needs to prove itself |
| Announce | The contact's first request (`GET /config/<device>`) doubles as the clock sync: its `Date` header sets `clock_skew_s` and `settimeofday`; then one telemetry post with `mode=3`, `boot_count`, `pending_files`, `pending_cold`, `clock_skew_s` |
| Sense | `lum` (mean of the decoded thumbnail) every wake; battery/charge not applicable (no divider wired) |
| Watch | 1/8-decode 200x150 RGB565 → 40x30 box-average gray thumbnail, kept in RTC memory across sleep; `dc_thumb_diff` against the last **recorded** thumbnail (`diff_l_thresh`) |
| Capture | UXGA 1600x1200 sensor JPEG, quality 10, from `esp32-camera` |
| Judge | MobileNetV2 α0.35 3-class gate (`animal`/`person`/empty), 96x96 int8, esp-tflite-micro + ESP-NN, motion-centred crop; keep if a label in `keep_labels` at ≥ `gate_pct`, else discard unless `keep_all` or the 1-in-`audit_n` audit; fail-open (gate error → keep, `det` omitted) |
| Record | JPEG + sidecar JSON to `/spool/<boot>/<seq>` on SD, standard meta plus `score` (drain rank) |
| Deliver | **Deferred to contact** (camera_operation.md §3): the spool is primary, not a fallback; drained ranked (score descending) up to `upload_cap`, then debug frames up to `debug_max`, each 2xx deleting the pair |
| Report | Telemetry only meaningful during contact, every `telemetry_s`, including mid-drain and mid-serve |
| Serve | `dusty_control` (`esp_http_server :8266`) starts right after the hotspot join and runs through the drain and the serve loop (`/status`, `/stream`, `/shoot`, `/refresh`, `/live`); the serve loop polls every 500 ms until `contact_idle_s` of silence (or `GET /live`), pinned open while `cfg.mode == "setup"`, hard-capped at `setup_secs` |
| Rest | Deep sleep `period_s` in live, or the night schedule (below); RTC keeps the thumbnail, counters, config; NVS keeps `cfg`/`boot_count`/`last_ts` across power loss |
| Setup | Phone opens `/setup` during contact (`/stream` computes a focus score via `dc_sharpness` on the preview's centre 100x75 and tracks `focus_best`; `/shoot` records + uploads one frame immediately; `/refresh` re-pulls config); `contact_idle_s` extends contact while the page is open; edits nothing on the board |
| Recovery | Control-plane only (no camera, no SD), never sleeps, checks `/firmware/<device>/version` every 60 s: entered by the button held ≥ 3 s at cold boot, or 3 consecutive `ESP_RST_PANIC` boots |
| **Contact** (`camera_operation.md` §5) | Button (or a pending firmware verify) → join hotspot (3 attempts if pending-verify) → `GET /config/<device>` doubles as the clock sync → announce telemetry (marks a pending-verify image valid on its first 2xx, with one retry before contact ends) → firmware check/OTA then config apply from the same GET body (LED: three quick blinks if `cfg` changed) → ranked drain of `spool` then `debug` (stops after 5 consecutive upload failures) → serve → final telemetry, radio off, `contact_n++`, reclaim, motion reference reset. A pending-verify image that never gets a 2xx clears NVS `fw_pending` and restarts for the bootloader to roll it back, rather than sleeping. |
| **Night** (`camera_operation.md` §6) | `lum < lum_night` for `night_confirm_n` consecutive wakes → night; sleep `predicted − night_margin_s` (median of the last 3 nights) then probe every `night_probe_s`; `lum > lum_day` on a probe → day, morning frame `why: boot` carries `night_s`; only the button wakes it early |

## Serial commands / log format

Console is USB-Serial-JTAG (`software/host/monitor.py PORT`); there is no
interactive command line, only `ESP_LOG` lines tagged `xiaocam1` /
`contact` / `judge` / `app_state` / `camera` / `gate`. One summary line
closes every wake:

```
I (xxxx) xiaocam1: wake_n=<n> cause=<cold|timer|button|other> lum=<0-255> diff=<0.000-1.000> why=<boot|motion|interval|heartbeat|none|manual> kept=<0|1> score=<float> awake_ms=<n> sleep_s=<n>
```

`kept` is 1 only when a frame was actually written to the spool this wake
(a `why` other than `none` does not guarantee a write — the gate can still
discard it). During a contact, `contact`-tagged lines report the join
result, the drain counts (`drain <tier>: uploaded N of M found`), and a
`contact done: sent=.. skipped=.. failed=.. pending=.. contact_n=..`
summary at the end. `judge`-tagged lines report each gate inference
(`animal=NN% keep=.. audit=.. ms=..`) and, once at boot, the arena
footprint (`gate arena: used/capacity B (SPIRAM)`).

## What sensorhub needs

(`PLAN.md` §13 — out of scope for this camera's firmware, but required on
the server side before the standard mapping above is fully useful.)

- `mode: 3` (contact) shown on the device page.
- `clock` correction of `ts` for frames recorded between two contacts
  (linear fit from `clock_skew_s`).
- `pending_cold` / `contact_n` shown on the device page.
- A `why: watch` debug-frame viewer, for tuning `diff_min_frac` /
  `diff_l_thresh` from `debug_frames` data.
- `score` shown on frames (the drain rank).

Also out of scope this pass: the N6, mesh (MeshCore), model retraining, and
an exposure ladder (left out so `lum` stays comparable across wakes).

## Bench gates

(`PLAN.md` §8, in order; each result goes in sarg.)

- [x] **BOOT wake — PASS 2026-09-16.** A GPIO0 press in deep sleep runs the
  app via the ext1 wake; it does not fall into ROM download mode. Serial:
  `wake_n=2…11 cause=timer cold=0`, then the press `wake_n=12 cause=button
  cold=0` (ext1 cause is only reported on a deep-sleep wake; RTC state intact).
  The button stays on GPIO0; an external field button can be wired in parallel
  with BOOT. (A 2026-09-15 attempt was invalid: the firmware was crash-looping
  and never slept — see `docs/phone_app_status.md`.)
- [ ] **Deep-sleep current** with the Sense board and card fitted, wired as
  in the tubecase (sarg says 1–4 mA leak to expect).
- [ ] **Hotspot join time** against the real phone on 2.4 GHz, 10 tries.
- [ ] **Upload throughput** through the phone for a ≥ 200-frame drain.
- [ ] **RTC drift**: `clock_skew_s` at every contact for two weeks.
- [ ] **Gate timing**: ESP-NN on, arena placement, ms per inference at 96 px.
